# Worklog v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A login-protected web app where a 3-person team logs findings (explanation + screenshots) per project per day, assigns tasks, and the lead sees a "Today first" overview per person.

**Architecture:** React SPA on Vercel talking directly to Supabase (Postgres + Auth + Storage). All permissions are enforced in the database (RLS policies + guard triggers). All Supabase calls are isolated in `src/data/` so the backend can later be swapped (self-hosted Supabase, then FastAPI) without touching UI.

**Tech Stack:** Vite, React, TypeScript, Tailwind CSS v4 (`@tailwindcss/vite`), React Router, TanStack Query, `@supabase/supabase-js`, `browser-image-compression`, Vitest + React Testing Library, Supabase CLI (local stack via Docker) + pgTAP for DB tests.

**Spec:** `docs/superpowers/specs/2026-10-29-worklog-design.md`

## Global Constraints

- **Hedi commits everything himself.** Never run `git commit`/`git push`. Each task ends with a checkpoint: stop, summarize the change, suggest a commit message.
- **Explain as you go** (from Hedi's CLAUDE.md): before each change, say in plain words what and why; introduce new patterns with the *why*.
- All Supabase imports only in `src/lib/supabase.ts` and `src/data/**` — enforced by ESLint `no-restricted-imports`.
- Data-layer functions return plain camelCase TypeScript objects (types in `src/data/types.ts`), never raw Supabase responses. Errors are thrown as `DataError`.
- Config only via env vars: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`.
- Schema changes only via SQL files in `supabase/migrations/`. No dashboard edits to schema.
- No Supabase features beyond Auth + Storage: no Edge Functions, Realtime, pg_graphql, DB webhooks.
- Store storage *paths* in the DB, never URLs. Path format: `findings/<finding_id>/<uuid>.webp` (or `.jpg` fallback).
- Bucket `finding-images`, **private**; images shown only via signed URLs, TTL 3600 s.
- Team timezone constant `TEAM_TIMEZONE = 'America/Chicago'`; "today" always means today there.
- Screenshots compressed client-side: max dimension 1920 px, WebP, quality 0.8, target ≤ 0.5 MB. Max 10 images per finding.
- Every table has RLS enabled. Public sign-up disabled. Nothing readable without login.
- Explanations are plain text; render with `whitespace-pre-wrap`, never as HTML.
- Names are never hard-coded; columns/dropdowns come from `profiles`.
- Everything on free tiers (Vercel Hobby, Supabase Free).

## Review Focus

1. **Late-evening logging:** a finding created at 23:30 Central must default to *that* Central date, not the next UTC day. → test in Task 5 (`todayInTeamTz`).
2. **Bypassing the UI:** a member calling the API directly to edit someone else's finding text, delete another's task, or delete a project must be rejected by the DB, while toggling another's finding status still works. → pgTAP tests in Task 3.
3. **Orphaned screenshots:** deleting a finding or project must remove its files from Storage, not just the DB rows. → integration tests in Task 4.
4. **Partial upload failure:** if 1 of 3 screenshots fails to upload, the finding still saves with the other 2 and the user sees "1 screenshot failed to upload" and can retry from edit. → tests in Task 4 (`createFinding` result) and Task 9 (form message).
5. **Wrong files pasted/dropped:** non-image files or an 11th image are rejected with a visible message, not silently dropped or uploaded. → tests in Task 6.

### Task 3: Permissions (RLS + guard triggers)

**Files:**
- Create: `supabase/migrations/20261029000002_permissions.sql`
- Test: `supabase/tests/permissions.test.sql`

**Interfaces:**
- Produces: SQL function `public.is_lead() returns boolean` (`security definer`, `stable`, reads `profiles.role` for `auth.uid()`).
- Policies implement spec §6 table exactly. Column-level rules are enforced by BEFORE UPDATE guard triggers, because RLS can't restrict *which columns* change:
  - `findings_guard`: if `auth.uid()` is neither `author_id` nor lead, raise `'only the author or lead can edit this finding'` when any column other than `status`/`updated_at` changes.
  - `tasks_guard`: if `auth.uid()` is neither `created_by` nor lead: allow only `status`/`done_at` changes, and only when `auth.uid() = assigned_to`; otherwise raise `'not allowed to edit this task'`.
- Policy summary (all `to authenticated`; `anon` gets nothing):
  - profiles: select all; no insert/update/delete from client.
  - projects: select/insert/update all; delete `is_lead()`.
  - tasks: select/insert all (insert `with check created_by = auth.uid()`); update all (guard trigger narrows); delete `created_by = auth.uid() or is_lead()`.
  - findings: select all; insert `with check author_id = auth.uid()`; update all (guard narrows); delete `author_id = auth.uid() or is_lead()`.
  - finding_images: select all; insert/delete when parent finding's `author_id = auth.uid() or is_lead()`.
